Module 1 · Getting Started
What Are Network Logs?
The foundational concept every Premium Support agent needs before touching DevTools.
📡
Every time a GHL user does anything — submits a form, fires a workflow, loads a funnel, books a calendar slot — their browser sends HTTP requests to GHL's servers. Network Logs capture every single one of these exchanges in real time. They are your source of truth when a client says "it's not working."
🔍 What Gets Logged
  • Every API call the browser makes to GHL
  • HTTP method (GET, POST, PUT, DELETE)
  • Status code returned by the server
  • Exact data sent in the request body
  • Full server response — including error detail
  • How long each call took (timing)
  • Response payload size
🎯 When You Need Them
  • Form/funnel submissions not saving
  • Webhooks not triggering
  • Workflow automations failing silently
  • Stripe or calendar integrations broken
  • SMS or emails not sending
  • Ad Manager accounts not appearing in dropdowns
  • Any "it worked yesterday" complaint
⚡ Why Network Logs Beat Guessing
🎯
Pinpoints Exactly What Failed
Shows the exact API endpoint that failed — not a vague error page.
💬
Plain-Text Error Messages
Server returns structured JSON with exact error descriptions.
⏱️
Cuts Resolution Time
Skip the 10 clarifying questions. The log tells you more than the client can.
Module 2 · Getting Started
Opening DevTools in Chrome
Step-by-step: how to open the Network tab and capture logs before reproducing a client issue.
⚠️
Critical rule: Always open DevTools and navigate to the Network tab before reproducing the issue. If you open it after, the logs are gone.
🖥️ Step-by-Step: Capturing a Network Log
1
Navigate to the GHL sub-account page where the issue occurs. Do not trigger the issue yet.
2
Open DevTools: press F12 (Windows/Linux) or Cmd + Opt + I (Mac). Or right-click anywhere on the page → Inspect.
3
Click the Network tab in the DevTools panel. You'll see a table waiting to record traffic.
4
Confirm the red ● Record button is active (it's on by default). Enable "Preserve log" checkbox to keep logs across page reloads.
5
Now reproduce the issue exactly as the client did — submit the form, click the button, trigger the workflow.
6
Filter by "Fetch/XHR" to isolate API calls. Look for rows highlighted in red — those are your errors.
7
Click a red row → check the Headers tab for the status code and Response tab for the full error body.
🔧 Useful DevTools Filters
  • All — every request (images, CSS, JS, API)
  • Fetch/XHR — API calls only (most useful)
  • Doc — HTML page loads
  • Search bar: type a keyword like "submit" or "workflow"
💡 Pro Tips for Support
  • Right-click a request → "Copy as cURL" to share exact call with devs
  • Right-click → "Save all as HAR" to export full log as a file
  • Ask clients to screenshot the red row + the Response tab
  • GHL also has in-app logs: Settings → Integrations → Webhook Logs

Reading the Log Viewer
Click any log row to inspect the full request and response. Practice this on every support call.

📖 Column Reference
Time
When the browser made the request. Correlate with the client's reported timestamp.
Method
GET = fetch, POST = create/send, PUT = update, DELETE = remove. Wrong method → 405.
Status
HTTP response code — your first diagnostic clue. 200=OK, 4xx=client issue, 5xx=server.
URL / Endpoint
The specific API path. Tells you which GHL feature was involved — forms, webhooks, contacts, etc.
Module 4 · Core Concepts
HTTP Status Codes
The code is always your first clue. Learn the groups first, then the specific codes you'll encounter in GHL.
🚦 The Five Code Groups
2xx
Success
Request worked as expected
3xx
Redirect
URL has moved or changed
4xx
Client Error
Bad request, auth fail, not found
5xx
Server Error
GHL server crashed — not the client's fault
💡
4xx = something the client or integration configured wrong.
5xx = GHL infrastructure problem — escalate, check status page.

Module 5 · Core Concepts
Request & Response Anatomy
What to look for inside each HTTP call — the parts that carry the real diagnostic information.
📤 Anatomy of a Request
Outgoing Request
POST /api/v1/forms/submit HTTP/1.1 Host: rest.gohighlevel.com Authorization: Bearer eyJhbGci... ← token Content-Type: application/json { "locationId": "loc_abc123", "formId": "form_991", "email": "", ← EMPTY! "phone": "555-123" ← bad format }
Authorization Header
The Bearer token or API key. Expired or missing → 401. This is the #1 cause of integration failures.
locationId
Every GHL sub-account request includes this. Wrong ID = data goes to the wrong account.
📥 Anatomy of a Response
Server Response — 422
HTTP/1.1 422 Unprocessable Entity { "error": "Validation failed", "fields": { "email": "Email is required", "phone": "Use E.164 format" }, "traceId": "tr_8821bb92" ← save! }
"fields" object
GHL validation errors list exactly which field failed and why. This is your diagnostic shortcut — read it first.
"traceId"
A unique error identifier. Always copy this when escalating to GHL engineering — it's how they trace what happened server-side.
✅
Golden Rule: Never diagnose from the status code alone. Always open the Response tab and read the body. The message and fields objects tell you the root cause in plain language.
